# HTTP API и протокол

Полная схема типов доступна у работающего координатора по `/docs` и `/openapi.json`. Здесь объяснён смысл протокола. Пользовательское REST API использует HTTP Basic поверх TLS; браузерные страницы — подписанную cookie и CSRF. Токен агента не даёт прав пользователя или SSH-администратора.

## Пользователь

| Метод и путь | Права | Действие |
|---|---|---|
| POST `/api/jobs` | operator | Создать и проверить параметры |
| GET `/api/jobs`, `/api/jobs/{id}` | viewer | Список и сводка |
| PATCH `/api/jobs/{id}` | operator | Общая квота, раздельные квоты, глобальные потоки |
| POST `/api/jobs/{id}/start`, `/pause`, `/resume`, `/stop` | operator | Управление состоянием |
| POST `/api/jobs/{id}/retry_failed` | operator | Явно повторить ошибки, включая completed-job |
| GET `/api/jobs/{id}/items?status=failed&offset=0&limit=200` | viewer | Результаты с фильтром и страницами |
| GET `/api/jobs/{id}/events` | viewer | Журнал задания |
| PUT `/api/jobs/{id}/workers/{name}` | operator | Назначить/отключить worker, задать индивидуальные потоки |
| GET `/api/workers`, `/api/workers/{name}`, `/api/workers/{name}/metrics` | viewer | Узлы и метрики |
| PATCH `/api/workers/{name}` | operator | Потоки, лимиты ресурсов, доступность |
| POST `/api/servers` | administrator | Добавить конфигурацию узла |
| POST `/api/admin/workers/{name}/probe`, `/update`, `/start?job_id=1` | administrator | Разрешённые SSH-действия |
| GET `/api/audit` | administrator | Аудит действий |

Пример создания одного задания:

```json
{
  "name": "Пример преподавателя",
  "source": "kinescope",
  "range_text": "[200810246,200810246]",
  "chunk_size": 10,
  "threads": 4,
  "worker_threads": {"worker-02": 6},
  "max_connections": 4,
  "global_rate_limit_rps": 10,
  "check_rate_rps": 5,
  "download_rate_rps": 5,
  "request_timeout": 15,
  "max_retries": 4
}
```

`worker_names: []` означает все доступные серверы, включая новые. Непустой список фиксирует выбранные серверы; добавление другого выполняется через PUT назначения. `worker_threads` имеет приоритет над глобальным `threads`. При изменении потоков сервера в интерфейсе устанавливается индивидуальное значение для его назначений.

## Агент

Каждый запрос содержит `X-Agent-Name` и соответствующий ему `X-Agent-Token`. Секрет берётся из окружения агента. Координатор сверяет имя в заголовке с именем в URL и картой токенов.

1. POST `/api/agent/register`: имя, версия `2.0`, host нового узла, исходные потоки. Административные настройки существующего узла не перезаписываются.
2. POST `/api/agent/{name}/heartbeat`: метрики, `job_id`, при активной работе также `chunk_id` и `lease_token`. Ответ содержит настройки и признак продления аренды.
3. POST `/api/agent/{name}/lease`: `job_id`. Ответ — `chunk: null` или блок с токеном конкретной попытки, `next_id`, `skip_ids` и настройками.
4. POST `/api/agent/{name}/permit`: идентичность аренды и `kind: check|download`. `granted: false` означает подождать `wait_seconds` и повторить запрос. Будущие слоты не бронируются.
5. POST `/api/agent/{name}/feedback`: HTTP-статус внешнего ответа. Координатор адаптирует общую нагрузку.
6. POST `/api/agent/{name}/state`: текущий ID и промежуточный статус; при начале скачивания также номер попытки.
7. POST `/api/agent/{name}/progress`: конечные результаты ID и история попыток. Проверка владельца и сохранение проходят в одной транзакции. `next_id` вычисляется сервером.
8. POST `/api/agent/{name}/complete` или `/fail`: завершить полностью подтверждённый блок либо вернуть остаток.

Служебная идентичность аренды:

```json
{
  "job_id": 1,
  "chunk_id": 9,
  "lease_token": "уникальное-значение-из-lease"
}
```

Токен блока не заменяет персональный токен агента. Первый отличает попытки одной работы, второй — рабочих участников.

## Ошибки и совместимость

- 401: неверный персональный токен или пользовательские данные.
- 403: чужое имя, неподходящая роль, неверный CSRF.
- 409: потерянная аренда, неправильный переход состояния, конфликт явного повтора.
- 422: некорректные параметры.
- При 409 агент прекращает текущую работу, а не продолжает запись под старой арендой.

Повторная отправка подтверждённого результата не создаёт новую запись и не заменяет старый конечный статус. Повтор `complete` одной завершённой попытки допустим. Аренда новой попытки получает новый токен, даже если имя агента осталось тем же.

Изменение с 1.x на 2.x требует обновления агентов вместе с координатором. Сохранённые данные мигрируют, но небезопасные запросы старого протокола без fencing token не принимаются.
